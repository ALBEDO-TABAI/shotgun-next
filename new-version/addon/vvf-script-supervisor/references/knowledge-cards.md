# 从记录到知识卡

## 四类知识

- **原则**：跨项目，由多个独立案例验证，换模型仍成立。例：多人场面没有共享空间关系就不进入逐镜。
- **启发**：候选原则，已有至少两个独立案例或导演明确设为规范，但还没跨模型或没排除反例。
- **当期参数**：模型版本、字数上限、最长秒数、分辨率、价格、成功率、重试次数、某模型对某写法的反应；必须带日期与来源，过期即失效。
- **项目设定**：某项目的角色、空间、视点、美术、连续性决定和用户口味。只在该项目有效。

用户的一次偏好默认是项目设定候选；模型的一次表现默认是当期参数观察。两者都不直接进入通用技能文件。CSV 与档案里的“知识类型”都用这四个值。

## 知识卡

```yaml
id: K-XXX
title: 一句可执行的判断
type: 原则 | 启发 | 当期参数 | 项目设定
claim: 主张本身
triggers:
  - 何时适用
procedure:
  - 怎么做
failure_signals:
  - 没有这样做时会看到什么
exceptions:
  - 不适用的情况
evidence:
  - source: Take 或提示词版本 ID、会议或用户原话
    note: 观察到什么
confidence: 低 | 中 | 高
valid_as_of: YYYY-MM-DD   # 当期参数必填
last_validated: YYYY-MM-DD
```

## 证据门槛

- 一次成功或失败：只记观察，不写规则。
- 同一提示词版本多次生成得到不同结果：可形成模型倾向，仍是当期参数；提示词不同的多条 Take 不算随机重复，只能各记观察。
- 至少两个独立镜头或场次出现同样因果，或导演明确设为创作规范：形成启发或项目设定。
- 跨模型仍成立、无关键反例、步骤可复现：升为原则。
- 先保留反例，不只收集成功样本。示例文件里的虚构案例不计入证据次数。

反思链：原始提示词、参考、参数与输出 → 可观察症状或成功点 → 根因假设 → 单变量修改 → 新结果对比 → 候选经验 → 证据复核 → 知识卡 → 更新对应技能位置。

## 项目风格档案

用 `assets/project-style-profile.json` 记项目口味：一次反馈记 `candidate`；用户明确确认或本项目多个样本成立记 `confirmed`；模型专属经验记 `model_specific` 并带 `valid_as_of`；被推翻的记 `deprecated`，不删除。`department` 用 VVF 的角色词：director、screenwriter、art、character、cinematography、producer、editor、sound、continuity、prompt。档案不回写用户原话，不成为第二份可编辑的定稿。

## 更新技能的门槛

1. 在 Take 账筛出“知识卡候选”不为“否”的记录，核对原始素材。
2. 合并重复结论，找反例与适用边界。
3. 判断应更新哪份技能的哪个位置：角色职责、表演方法、编译规则、审片路由、项目档案。
4. 先写知识卡与证据，再改对应文件；保留 `last_validated`。
5. 不把原始项目的角色或场景设定写成跨项目原则。
6. 新证据推翻旧结论时标“已修正”或“已降级”，不静默覆盖历史。

复盘按事件触发：用户交来一批新审片或生成记录，或明确要求更新时运行；不按固定周期。
