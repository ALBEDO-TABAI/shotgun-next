# 1. 硬条件与软目标分开

- 包装错误、未提供必需版本等已确认问题，不应被“画面很美”的高分平均抵消。先检查必要条件，再比较可协商效果。
- 硬条件不能由评审者临时发明：原项目未要求名称全程清楚，就不能在交付时把个人偏好升为验收规则；新增要求作为**变更**讨论。硬条件来源见 [拆 brief](/ideation/brief-decomposition.md)。

# 2. 不相互支配的方案需要明确价值选择

A 更易读清动作但空间更说明性；B 更强调表面感但需更长时间辨认用途。若都满足硬条件，不必编造“客观总分”；说明本项目更优先哪项目标，写清选择理由和代价。承认其中包含项目价值判断，并不降低专业性。

# 3. 总分容易隐藏什么

权重不明、维度重复、把偏好伪装为测量、高分抵消严重错误。确需评分时，保留分项定义、权重来源、硬条件和不确定性，不只公布一个数字。

# 建议的决策状态

**条件满足 ／ 需修改 ／ 待验证 ／ 可接受取舍**——比伪精确的综合分更便于执行。（这是 [四种结论状态](/inference/four-conclusion-states.md) 的评审版。）

# 评价结果进入下一轮

- 每条已接受的问题对应一个修改对象与复核条件；尚未确认的问题先安排获取证据，不直接开技术处方。
- 修改后保留前后版本与实际变化；旧问题不能因换文件名重新出现，也不能未复核就自动关闭。
- 保存为案例时记录失败条件与适用范围：“某种高光遮住某种标签”不应归纳成“高光不好”，应保留标签、对象角度、显示尺寸与具体失效关系（进入 [规则卡](/transfer/rule-card.md)）。
