# 三层不能互相证明

| 层 | 内容 |
|---|---|
| **意图层** | 希望观众看见什么关系 |
| **请求层** | 提示词、参考输入和工具设置写了什么 |
| **结果层** | 实际生成或加工得到的画面呈现了什么 |

请求中写“50mm、浅景深、柔和轮廓”只记录了请求；结果符合某种外观，也不说明它通过真实镜头实现。使用 03、04 模块的观察与推断边界（[四个层次](/breakdown/four-layers-and-evidence-chains.md)、[四种结论状态](/inference/four-conclusion-states.md)）。

# 优先传递可见要求，再附候选实现语言

通用描述结构（**不是针对任何模型的最优提示词**）：

> 先交代对象与动作。说明初始可见和不可见的信息，给出关键对象的关系与画面边界。描述运动或显露触发条件，并说明结束时必须达到的状态。最后再附加希望尝试的焦段、光影或质地语言，以及不可改变的对象信息。

例：与其只写“电影感、微距、梦幻”，不如写“接触点必须可辨；手移开后产品名称完整；识别阶段不再继续大幅运动；高光不得遮住名称”。参数词可补充，不能代替结果要求。（结构同 [镜头状态说明](/ideation/shot-state-description.md)。）

# 检查生成结果的两个层面

1. **技术层**：对象、结构、文字、运动连续性、画面稳定性；参考 VBench 的多维框架，不压成模糊整体印象 [1]。
2. **任务层**：是否真的先接触后识别，信息是否在所需时间开放，变化是否有依据。技术稳定也可能没完成任务；有魅力的局部也可能含不可接受的对象错误。

不存在仅凭文本就能保证所有模型可靠执行的通用流程；工具与输出变化需通过实际案例检验，而不是由 skill 自我宣称通过。

# 改写提示不是唯一反馈动作

| 问题 | 动作 |
|---|---|
| 任务矛盾 | 修改 brief |
| 关系不可行 | 改变构想 |
| 材料或对象无法保持 | 改变实现策略 |
| 局部正确但时间失败 | 重点处理动态 |
| 只是输出裁切失效 | 不重做整个生成链 |

与 [反馈回到正确层级](/ideation/feedback-routing-layers.md) 一致。成熟技能应指出问题层级，而不是对所有问题都追加更多形容词和否定词。
