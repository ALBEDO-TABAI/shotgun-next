# 公开依据

- 官方说明项目包含发布影片与灵活视觉系统：既需要清楚介绍平台，又希望维持抽象、美观且不过度陌生的世界，并避免过于明显的视觉隐喻。来源镜像见 [C04 参考条目](/references/c04-tendril-microsoft-hybrid-work.md)。
- 查验范围：项目目标、方法与视觉系统公开说明。这些是该项目的**表达目标**，不是当前产品规格、服务能力或性能的核验。

# 可提取的方法（本包提取，不是原团队用语）

- 在具体内容身份与抽象空间之间分工：资料、设备、模块或权限保持清楚；空间、过渡、质感提供体验。
- 脚本先写关系：谁访问什么、什么保持一致、什么被转换、什么只对某个角色可见。然后才选择图块、界面、装置或空间。
- 不要从「云端」反推必须出现云朵。

# 原创迁移：跨设备资料接续（虚构项目）

虚构功能只包括打开同一资料和保留阅读位置，**不包括同步编辑或自动总结**。

1. 建立一份有唯一标题和页码的资料；
2. 另一个设备视图出现同一标题与页码，说明对象延续；
3. 改变外部工作空间，但资料身份保持；
4. 两个视图并置，准确文字说明本例功能。

抽象部分可以改变容器、空间层次和移动路径；不应改了资料内容后仍声称「一切完全相同」。若产品实际功能不同，要**修改事实卡**，而不是让漂亮空间替它作保证。

# 回修与分叉

- 方向甲：以实体文件夹式图形建立熟悉感，转换清楚但可能较常规。
- 方向乙：以独立窗口与稳定标识组织空间，少用现实隐喻，可能更简洁但更依赖标签。
- 比较时保持信息内容与时间预算接近，不要拿精修甲和粗稿乙直接比审美。
- 设计需求是稳定资料身份、设备视图、状态、权限、同一内容的位置锚点；不是「十个科技场景」，也不是每个设备各生成一份不同文件。

# 迁移要点

抽象的自由应主要用于表达载体，而不是用来取消系统关系的准确性。

# 最容易误借的东西

云朵、光线等泛化隐喻。
