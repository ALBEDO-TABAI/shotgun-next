# 要点

**步骤。**

1. 写出最终要被理解的判断。例：「两个模块可以组合使用」。
2. 反问它需要哪些前提。上例至少依赖：它们是两个不同对象；存在对应接口；连接后身份没有消失。
3. 把前提嵌入动作，不必给每个前提单独拍一段说明。
4. 用极简记号标出关系，区分硬依赖与可交换顺序。

**写作记号**（只用于写作，不是正式学术记法）：

| 记号 | 含义 |
|---|---|
| `A → B` | B 的理解依赖 A |
| `A ≈ B` | 二者可比较或类比 |
| `A ∥ B` | 顺序可交换 |

# Examples

「一页」教学灯例：

```text
产品身份 → 折叠前后对照
按钮动作 → 本次亮灯的原因
光面局部 → 光面属于书页的重新定位
```

但「折叠」与「开关」并不存在必然的产品技术依赖；本例先展开再开灯只是选择的演示顺序，**不能据此编出「折起时禁止点亮」的新规格**。

# 适用边界

- 依赖图的价值在于告诉作者：哪些顺序必须保护，哪些只是可以优化的当前选择。
- 过度把每个先后都标成硬依赖，会阻止短版和美术回修。
- 演示顺序不等于产品技术依赖，不得由此补造事实。
