# 要点

## 何时调用

先后与时长不清；分不清是世界变了还是观看范围变了；「看不懂」但不知道该修哪里。不需要每次全量输出六篇。

## 输入

- 已选表达命题与路线（来自 [任务路由与路线生成](/skills/task-routing-and-route-generation.md) 或 [创意机制生成](/skills/idea-mechanism-generation.md)）；
- 产品事实与交付条件（时长、是否有声、版本）。

## 步骤

1. 用 [三线联合编排](/frameworks/three-line-orchestration.md) 分开世界、信息、时间三条线。
2. 标出真正改变的变量与只改变观看范围的部分（[状态变化的四种来源](/frameworks/four-sources-of-state-change.md)），判断 [关键中间态](/methods/key-intermediate-state-test.md)。
3. 确定 [身份锚点](/frameworks/information-gain-and-identity-anchors.md) 与 [披露写法](/frameworks/four-disclosure-modes.md)。
4. 用 [依赖排序](/methods/dependency-ordering.md) 区分必须保护的顺序与可交换顺序。
5. 按 [内容职责划分节拍](/frameworks/beat-as-content-duty.md)，为每段选定 [连接](/frameworks/eight-segment-connections.md)。
6. 分配 [声音与文字职责](/frameworks/sound-and-text-duties.md)，做 [时间预算](/methods/time-budgeting.md)。
7. 填写 [编排工作表](/templates/orchestration-worksheet.md) 并完成联合检查。

## 输出

有职责、有连接依据、有暂定时间的内容节拍；仍待检验的观看效果单独标为假设。

## 退出条件

- 每个主要节拍都有职责；
- 世界变化与披露变化不混用；
- 必要前提可追踪；
- 总时间可核算；
- 关键动作有足够定义；
- 仍待检验的观看效果被标为假设。

## 去向

- 完成后交第 05 篇写正文与需求：[初步剧本写作与设计交接](/skills/script-writing-and-design-handoff.md)。
- 机制本身不成立时返回第 03 篇：[创意机制生成](/skills/idea-mechanism-generation.md)。
- **不要**直接堆生成提示词。

# 适用边界

- 「观众获得」一律写成设计目标，不写成已观测结果。
- 不补造产品规格：演示顺序不等于技术依赖。
- 本接口是知识资料中的执行约定，不是已安装或跑通的 agent；没有做过真实 agent 评测。
