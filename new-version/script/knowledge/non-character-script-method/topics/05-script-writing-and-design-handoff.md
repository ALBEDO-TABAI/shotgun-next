# 本篇回答什么问题

初步剧本怎样写，才能**直接产生设计需求**？一句「精美盒子打开，内部世界舒展」不足以制作；提前写死焦距与提示词又剥夺了美术提案空间。本篇给出中间层：写清必须发生的内容、必须保持的关系、下游需要解决的设计条件，而不提前指定所有实现。

# 输入与产物

- **输入：** 已选表达命题与路线（[01](/topics/01-capability-and-creative-path.md)、[03](/topics/03-idea-generation-and-visible-process.md)），状态／披露／时间节拍结构（[02](/topics/02-object-information-time-orchestration.md)）。
- **产物：** 可阅读初稿；内容节拍表；有消费位置的设计需求；待回修事项与交付说明。
- **下一站：** 资产与分镜构思；升级、改版与回修进入 [06](/topics/06-optimization-validation-and-multi-agent-revision.md)。

# 核心主张

1. 「可被设计」不是「所有设计已完成」，而是每个关键表达都有可接手的问题。
2. 正文、节拍表、实现描述是同一内容的三个层级；节拍表不新造情节，实现层不更换主张与因果。前置的是表达约束，不是模型参数。
3. 句子要有对象身份、动作方向、空间关系、披露与结果；动词暴露设计任务，先明确动词的真实性层级再提取资产。
4. 限制应具体到**关系**，而不是具体到不必要的唯一实现。
5. 设计需求不止资产清单，还包括状态、行为、关系、可见性、准确文字与声音职责；需求数量不等于资产数量或生成调用次数。
6. 每条关键需求知道为什么存在、谁使用、怎样判断可用（双向对应）；没有使用位置的需求是负担，没有设计支持的节拍是纸面愿望。
7. 「已列出」不等于「已可用」；状态只说明进展，不替代用户确认。
8. 交接前做消费演练；接手者不补剧情，只返回无法判断的条件或在自由范围内提案。

# 证据骨架与边界

| 依据 | 可以据此说什么 | 本包进一步提出什么（综合，非来源结论） |
|---|---|---|
| NASA 需求管理 [2] | 需求应能回溯来源、对应下游实现与验证，并避免无依据的额外要求 | 只迁移**最小对应思想**：每个关键设计需求知道为什么存在、谁使用、怎样判断可用；不移植航天工程的完整管理制度 |
| 材料体验设计（MDD）[3] | 提供从体验意图回到材料与作用关系的研究入口 | 把「资产清单」扩展为对象、状态、行为、关系、可见性与准确文字的设计需求 |
| Ordinary Folk 公开流程 [4] | 该机构的实践中，脚本、设计、动画与声音分工又协作 | 编剧—美术主责之外的摄影、声音、制作三个接口 |

- 本篇的交付格式是面向当前 AI 团队的建议，**不是行业统一剧本标准**，也不是上述来源共同验证出的标准。
- 「一页」与其余示例均为原创虚构教学设定；没有执行视频生成、付费调用、受众测试或真实 agent 评测。
- 整包证据分层见 [证据与使用边界](/principles/evidence-and-use-boundaries.md)；结构校验范围见 [包结构检查](/checklists/package-structure-checks.md)。
