# 要点

| 类型 | 示例 | 处理方式 |
|---|---|---|
| **实现内调整** | 在保持单铰链可见的前提下调整观察方向 | 专业端可执行，更新自身方案及必要引用 |
| **内容关系变化** | 把先见结果后解释，改成先作用后结果 | 提案回到编剧／导演，更新正文、节拍及依赖 |
| **事实或任务变化** | 改成自动感应，或用户取消操作说明 | 先核验事实或确认新任务，再重新分配内容 |

**类型不是按改动字数划分的**：

- 「产品出现」改成「产品生成」，只变两个字，却可能改了整片含义。
- 某一背景用了大量新纹理，也可能完全不触及内容。

判断时问三件事：承载者、因果或披露顺序变了吗（内容关系）？产品事实、主张或用户已确认的任务变了吗（事实或任务）？都没有，才是实现内调整。

# 适用边界

- 分类是本包的交接约定，借用了配置管理中区分基线、提案与已落实变更的思路（来源与限度见 [调研为回修提供了什么](/principles/what-research-supports-for-revision.md)），但不引入完整审批制度。
- 分类结果决定的是「谁来处理、更新哪里」，不评价改动好坏；美术提出的内容关系变化可以是有效增益。
