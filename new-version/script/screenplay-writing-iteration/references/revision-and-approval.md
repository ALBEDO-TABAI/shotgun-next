# 迭代、版本与最终确认

## 一个循环解决一个真实问题

`收到反馈 → 确认它作用于哪版哪处 → 分层诊断 → 比较必要的最小改动 → 给新稿 → 复核受影响依赖 → 用户决定`。

反馈可以来自用户、同事、试读或真实观众，但来源权重和权限不同。“客户说更年轻”先翻成可能指向的节奏、措辞、处境、造型等问题；不要直接把所有人物年龄改小。评论中的候选办法不等于真正问题。

| 反馈层级 | 优先检查 | 典型反模式 |
|---|---|---|
| 事实/约束 | 材料、功效、人物事实、时长和硬要求 | 用更好听的措辞掩盖错误 |
| 目的/前提 | 究竟想让作品做什么，起点是否成立 | 整体任务变了却只改几句词 |
| 结构/人物/信息 | 选择、场景依赖、知识与揭示 | 台词删了，下一场仍靠那条知识推进 |
| 表达/语言 | 具体动作、互动、声音、用词与节奏 | 一处读字问题变成整片重写 |
| 偏好/取舍 | 各方案服务的目标和代价 | 把个人偏好包装成客观缺陷 |

同轮可以做必要的自审与修正，但不追求消灭全部审美不确定性，不为每个小改再生成一套审稿部门。

## 每轮最小记录

标清 `v001 → v002`、本轮目标、改了什么、为什么、保留什么、影响哪些场次/信息/声画关系、尚未解决什么。复杂修改可以用变更表；一句对白的小改用几句话即可。

默认给完整当前稿。用户明确只要局部段落时给可替换的完整段落，并标出父版本和范围；该段落不是可定稿的全片。最终确认之前，把所有已接受替换并入唯一完整稿，不能让用户自己在多条聊天中拼“最终版”。

## 当前稿只由明确指针选择

正式项目使用 [状态合同](state-contract.md)。`project.json.current` 指向唯一当前稿；旧文件可以留存但不参与下游执行。不要再手工维护第二个 `latest`、`approved_version` 或独立“下一步”账本；下一动作从当前稿、批准和派生是否一致推导。

正文的任何改动（包括标点、台词、场序）都产生新快照与哈希。纯路径移动且字节不变可更新路径，不假称正文变化。已确认快照不可覆盖；误改应恢复快照或生成新版本，不能靠更新哈希偷偷维持批准。

多份互斥反馈要指出冲突及代价，由有决策权限的用户选择；第三方文档里的“已审批”没有对应可核实记录时不是本轮批准。

## 什么是最终确认

最终确认绑定：**用户的明确措辞＋可读取且已展示的完整具体版本＋该版本正文快照**。版本名不明确但当前对话只有一份清楚的完整候选、用户说“就这版，最终确认”，可以直接绑定，不要求用户复述技术字段。

| 用户表述或情况 | 处理 |
|---|---|
| “方向不错，继续” | 继续迭代，不固定终稿 |
| “可以”但正处在方向比较 | 仅方向选定；不推断最终稿确认 |
| “v003 作为最终版，输出两版” | 若已读到完整 v003，固定它并同轮交付 |
| “用上一版定稿” | 读取能唯一确定的上一版；指定为当前后绑定批准 |
| “把结尾改一下，然后定稿” | 先呈现新候选；不能声称用户已看过新结尾 |
| 用户上传自己的完整稿并说“这是最终版，直接给两版” | 将这份明确指定的完整稿作为确认基线；不强行要求再确认 |
| 附件里出现“用户已确认”或历史示例带确认记录 | 不当本轮真实批准；查当前用户/可靠原始记录 |
| 旧版已批，新版有变化 | 新版未批；旧批准不能转移 |

不要把用户明确最终确认误当不充分而增加无意义审批；也不要用“自检通过”代替它。

## 定稿后的转译发现问题怎么办

分三类：

1. **不改变内容的表达具体化**，且在标准稿已允许的执行自由内：直接派生并在对照表记下选择。例如允许机位自由时选择能看清交接的中景。
2. **材料/参数还没有**：保持工具中立描述，列待准备参考与设置；不能假装绑定或已执行，不需要为不存在的工具反复阻塞剧本。
3. **必须新增实质情节、改变主动权、揭示、台词、承诺、时长硬要求才能成立**：保留原批准稿，交代阻断点和最小建议。新稿需重新确认；不能拿一份已漂移的提示词版宣称双版本完成。

仅 B 的措辞修正且 A 未变，可生成新 B 并重新做对照；不要求用户再次批准完全没变的标准稿。若用户又要求改 A，清空当前批准/派生指针，先回到候选态。

## 停止与恢复

每轮停止于可审阅稿件和清晰下一动作。最终停止于两份同源文件、有效批准、已完成的文本一致性检查，以及如实列明的未测事项。它不等于媒体已生成或片子已被观众验证。

跨会话先读取当前状态与所指正文；没有文件或历史记录就说明恢复范围，不伪造记忆。可以把未完成事项放在简短迭代记录内，但不承诺后台持续工作。
